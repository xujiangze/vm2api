# 升级手册（线上 Ubuntu 24 · docker compose 部署）

线上从私有镜像 `ghcr.io/xujiangze/vm2api` 升级的标准流程。发布新镜像的流程见[私有发布规范](./私有发布规范.md)，本版本包含哪些改动见[私有发布日志](./私有发布日志.md)。

## 前提

- 部署目录为最初 `install.sh` / compose 创建的目录（含 `docker-compose.yml` 与 `.env`）
- 数据全部在宿主绑定挂载里（`vms/` 账号记录、`data/` SQLite 与配置、`bin/`、`share/`、`src/config/`），**升级镜像不动这些数据**
- 槽位容器由控制面管理，控制面重启后会自动恢复，无需单独操作

## 一、升级前检查

```bash
uname -m          # 必须是 x86_64；aarch64 需改用 arm64 构建（见发布规范）
docker ps --format '{{.Names}} {{.Image}} {{.Status}}' | grep vm2api   # 记下当前镜像 tag（回滚用）
docker exec vm2api cat /opt/vm2api/VERSION 2>/dev/null || true
```

建议升级前对部署目录做一次快照：`tar czf /root/vm2api-backup-$(date +%F).tgz vms data .env docker-compose.yml`（在部署目录的父目录执行，注意 data/ 体积）。

## 二、执行升级

编辑部署目录 `.env`，设置：

```bash
VM2API_IMAGE=ghcr.io/xujiangze/vm2api
VM2API_IMAGE_TAG=v1.4.061-xjz.1        # 换成目标 tag
```

然后：

```bash
docker compose pull && docker compose up -d
```

> 首次从上游镜像（`ghcr.io/dofastted/vm2api`）切换到私有镜像时，操作完全相同——`.env` 的这两个变量覆盖 compose 默认值，仓库文件一行不用改。

## 三、升级后验证

```bash
# 1. 容器在跑、镜像已切换
docker inspect vm2api --format '{{.Config.Image}} {{.State.Status}}'

# 2. 健康检查
curl -sS http://127.0.0.1:8787/health

# 3. 日志无启动报错
docker logs vm2api --since 2m | tail -20
```

**功能冒烟**（针对 v1.4.061-xjz.1 的私有修复，每次升级到含此修复的版本只需做一次）：

```bash
# ① 续接回归：master key 双账号钉定（旧版必炸 Invalid previous_response_id，修复后应 200 且答出暗号）
# 第一轮（钉账号 A）：
curl -s http://127.0.0.1:8787/v1/responses \
  -H "Authorization: Bearer $MASTER_KEY" -H "x-kin-vm: $VM_A" -H "content-type: application/json" \
  -d '{"model":"gpt-5.4","stream":false,"input":[{"type":"message","role":"user","content":[{"type":"input_text","text":"记住暗号：pineapple"}]}]}'
# 记下 .id → 第二轮（钉账号 B + 续接）：
curl -s http://127.0.0.1:8787/v1/responses \
  -H "Authorization: Bearer $MASTER_KEY" -H "x-kin-vm: $VM_B" -H "content-type: application/json" \
  -d '{"model":"gpt-5.4","stream":false,"previous_response_id":"<上面的id>","input":[{"type":"message","role":"user","content":[{"type":"input_text","text":"暗号是什么？"}]}]}'
# 预期：回答含 pineapple；面板日志第一轮 replay_captured=true、第二轮 replay_expanded=true

# ② 走一遍 sub2api 真链路多轮对话（≥5 轮），确认无 Invalid previous_response_id、上下文连贯
```

## 四、回滚

`.env` 里 `VM2API_IMAGE_TAG` 改回升级前的 tag → `docker compose pull && docker compose up -d`。数据卷格式不做破坏性迁移，回滚只是换镜像。

紧急行为回退（不换镜像）：确认线上 `.env` 增加 `KIN_CODEX_PREVIOUS_RESPONSE_EXPANSION=0` 并 `docker compose up -d`，可单独关闭"本地展开"回到旧的账号钉定续接。

同理，`.env` 增加 `KIN_UNOFFICIAL_CONVERSATION_GUARD=0` 可单独关闭"非官方请求首跳补齐对话结尾"，回到收到 prefill 400 后重试时才修。

## 五、升级后 24h 观察项

- 上游错误中 `Invalid previous_response_id` 出现次数 → 应为 0
- 上游错误中 `does not support assistant message prefill` 出现次数 → 应明显下降（CRAG v2 槽位仍可能出现，靠重试修复）
- `previous_response_not_found` 400 计数 → 少量正常（重启后第一批续接），持续大量需排查
- 续接轮 `input_tokens` 偏高属预期（每轮携带全量历史），计费随之变化
- 进程内存平稳（回放缓存上限 64 MiB + LRU）
