# 私有发布日志

记录 `xjz` 分支相对 `main`（上游同步分支）的每一个私有提交：动机、改动文件、与上游同步（merge main）时的注意点。**新增私有提交时必须同步登记本文件**（模板见文末）。

背景：线上链路为 终端客户端（Codex CLI / Claude Code 等）→ sub2api → 本网关 → ChatGPT Codex 后端，私有改动主要围绕这条链路的兼容性。

### 1. `054e0f36` fix(protocol): strip chat-only stream_options.include_usage

- **动机**：sub2api 转发的请求携带 Chat Completions 专属的 `stream_options.include_usage`，上游 Responses 端点对未知参数返回 400。
- **改动**：`src/lib/protocol/codex-convert.mjs` 的 `stripUnsupportedCodexFields` 剥离该字段；`test/unit/codex-convert.test.mjs` 补用例。
- **同步注意**：`codex-convert.mjs` 是上游高频改动文件；冲突集中在 `stripUnsupportedCodexFields` 函数体内，保字段剥离逻辑即可。

### 2. `76fd5a7e` feat(codex): HTTP Responses 本地展开 previous_response_id

- **动机**：sub2api 链路使用 `previous_response_id` 服务端续接；网关多账号池调度会把续接请求路由到未创建该响应的账号，上游报 `Invalid previous_response_id`。改为网关本地展开成全量历史，字段永不出网关，对话不再锁定单一账号（决策记录见 `docs/adr/0001-responses-local-expansion.md`）。
- **改动**：
  - 新文件 `src/lib/protocol/http-replay.mjs`：进程级回放缓存（按 API key 隔离，默认 256 条 / 64 MiB，LRU）
  - `src/lib/protocol/handle-codex.mjs`：展开钩子（`converted` 校验后，未知 id 返回 400 `previous_response_not_found`）、快照捕获（`responseCompletedFromSseLine` 解析终态事件 + 成功路径 `remember`）
  - 复用 `responses-ws.mjs` 已导出的 `expandPreviousResponse`
  - `docs/API.md`、`CONTEXT.md`、测试 `test/unit/http-replay.test.mjs` + `test/unit/handle-codex.test.mjs`
  - 开关：`KIN_CODEX_PREVIOUS_RESPONSE_EXPANSION=0` 回退旧行为
- **同步注意**：`handle-codex.mjs` 是上游最大、改动最频繁的文件，冲突概率最高。合并时要保住三处钩子的位置：① 展开钩子在 `toCodexResponses` 成功分支之后、`applyOpenaiWashLog` 之前；② SSE 捕获在 `onEvent` 的 `imageGenUsageFromSseLine` 之后；③ 提交在 `delivered` 块 `bindSticky` 之后。`pickCodexCandidates` 的 `continuesResponse` 逻辑**故意保留**（kill-switch 回退路径），上游重构调度时勿删。

### 3. `9e3c86f3` fix(identity): 认下划线 session_id / conversation_id 会话头

- **动机**：Codex 系客户端与 sub2api 用下划线形式（`session_id`）发会话头，网关白名单只认连字符（`session-id`），粘性路由取不到稳定标识。
- **改动**：`src/lib/identity/identity-rewrite.mjs` 的 `CALLER_SESSION_HEADER_KEYS`、`src/lib/pool/sticky-router.mjs` 的 `DEFAULT_STICKY_HEADER_KEYS` 各加 2 个下划线条目；`handle-codex.mjs` 的 `sessionFrom` 同步；`test/unit/identity-rewrite.test.mjs` 补用例。
- **同步注意**：三处都是常量列表追加，冲突好解；若上游重构身份提取，确保下划线 `session_id` / `conversation_id` 仍能被识别。

### 6. `<本提交>` fix(protocol): 非官方请求首跳补齐对话结尾，修复 assistant message prefill 400

- **动机**：链路 Codex CLI → litellm → sub2api → 本网关 → Claude 上，sub2api 的 Responses→Anthropic 转换会丢掉它不认识的工具输出项（`local_shell_call_output` / `mcp_tool_call_output` / 未声明的 `custom_tool_call_output`），到网关的对话以 assistant 结尾。Claude 4.6 及以后不再支持 prefill，上游 400「This model does not support assistant message prefill. The conversation must end with a user message.」。原先网关只在收到 400 后重试时才修，多一次往返；一次性修复名额被别的 400（如签名）用掉后，这个错误直接返回给客户端。
- **改动**：
  - `src/lib/protocol/request-rectifier.mjs`：新增 `ensureConversationInvariants`（没结果的 tool_use 补占位 tool_result；结尾是 assistant 时补一条 `continue` user 消息）、`modelSupportsAssistantPrefill`（4.6 之前的模型仍支持 prefill，不补 `continue`；新模型和不认识的 id 都补）、开关 `conversationGuardEnabled`。
  - `src/lib/protocol/outbound-attempt.mjs`：HTTP 直连线路在 `prepareOutboundEnvelope` 发送前最后一步执行检查，setup-token / API key 凭据也执行。
  - `src/lib/protocol/handle-protocol.mjs`：CLI-hop 线路在 `prepareCliHopBody` 之后执行同一检查。官方 Claude Code 流量首跳两条线路都不改。
  - `src/lib/pool/upstream-error-policy.mjs`：prefill 错误识别补 `/assistant message prefill/i`，prefill 分类不再受 `repaired` 限制。
  - `src/lib/pool/failover-runner.mjs`：prefill 修复不占一次性修复名额，但自身只修一次。
  - 测试：新文件 `test/unit/unofficial-conversation-guard.test.mjs`；`failover-runner` / `upstream-error-policy` / `persona-outbound-contract` 补用例。
  - 开关：`KIN_UNOFFICIAL_CONVERSATION_GUARD=0` 关闭首跳检查，回到收到 400 后重试时才修。
- **同步注意**：
  - `outbound-attempt.mjs`：检查必须在 `sanitizeAnthropicBodyForBetaTokens` 之后（它会把结尾的 system 消息挪走，重新露出 assistant 结尾）、`sealClaudeCodeCch` 之前（封印要覆盖最终 body）；也不能挪回 `rectifyUnofficialRequest`，否则缓存断点会落在合成的 `continue` 上（`request-rectifier.test.mjs` 里上游原有的"首跳不补 continue"测试会拦住）。
  - `handle-protocol.mjs`：检查必须在 `prepareCliHopBody` 之后、`ensureBillingAttribution` 之前；放到前面，`materializeAutomaticCache` 会把缓存断点打到 `continue` 上。
  - `failover-runner.mjs` 的修复分支和 `upstream-error-policy.mjs` 的 400 分类是上游常改的地方，冲突时保住"prefill 不占名额、但只修一次"。
  - CRAG v2 print 线路有意没加：上游注明改写已发出的历史会让工具续接报 history mismatch，这条线路仍靠 400 后重试修复。
  - 新模型若仍支持 prefill，要加进 `modelSupportsAssistantPrefill` 的正则；默认按不支持处理。
  - 根因在 sub2api：网关补 `continue` 只能让请求不报错，被丢掉的工具输出救不回来。

### 7. `<本提交>` docs(二开): 私有发布 tag 改用 xjz-日期格式

- **动机**：原格式 `v{上游VERSION}-xjz.{N}` 带 `v` 前缀，推 git tag 会触发 `.github/workflows/release.yml` 自动构建并推镜像（含 `latest`），与"私有发布不走 CI、不用 latest"冲突；且上游每次推进 VERSION 序号都要重算，日期格式与上游版本解耦（基于哪个上游版本记在 tag 说明与本日志）。
- **改动**：`私有发布规范.md` Tag 规范改为 `xjz-{YYYYMMDD}`（同日多版加 `.2`）；`AGENTS.md`、`升级手册.md` 的 tag 示例同步；历史已发布 tag 不改名。
- **同步注意**：纯文档，无代码冲突。
